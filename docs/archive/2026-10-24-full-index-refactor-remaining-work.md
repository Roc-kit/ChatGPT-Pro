| P0-4 | “清除索引”与“清除完整 JSON” | 两个**独立操作**：清索引不清原始 JSON；清原始 JSON 不清索引。均仅作用于当前已确认账号、二次确认、显示删除量；不动未归属旧 v1 索引和其他账号，不动已下载文件或 ZIP 分卷。需要处理清理后完成状态/缓存命中/后续自动重建，防止清完马上无提示重建。 | popup/*、scripts/local-data-store.js、scripts/background.js |

P0-4 的推荐默认行为：清索引后保留首次授权记录，但重置首次索引完成标记，并将自动更新置为关闭，须由用户主动重新建立索引后才恢复自动更新；清完整 JSON 后仍保留可搜索的现有索引，但未来缓存缺失时应正常按需抓取，不能错误认作“完整 JSON 命中”。执行清理时如果存在相关活跃任务，先提示用户暂停或取消，不在任务持续写入期间静默清除。数据库读写采用当前账号范围的事务，不能整库 deleteDatabase。

### P0-B：统一请求冷却（S3 必须补齐）

**现状：** scripts/api-handler.js 中 scheduledConversationDetail() 已用 IndexedDB 账号级详情租约与共享 429 冷却；fetchRegularIncremental()、fetchProjects()、fetchProjectIncremental() 与 runSync() 仍独立请求、重试和等待。

要求：

1. 明确区分“详情单并发”和“其他目录 API 请求”，**至少保证同账号遇到 429 后所有相关批量请求都读取同一个持久化冷却截止时间**；可复用现有 accounts 状态，不要再建第二套任务调度器。
2. 目录/项目请求遇 429 时优先尊重 Retry-After，没有时递增退避；冷却期不靠快速重试绕过官方限制，到期恢复未完成操作。临时网络超时可按已有受控重试处理。
3. 401/403 不能无限重试；全量首次扫描不得因失败而伪造“已完整扫描”，原有目录与索引保留。
4. 对无法完成的连续失败设置**简单、可观察、可恢复**的暂停规则，不要无限消耗请求；先沿用现有单条最多 3 次重试，跨项失败达到阈值时使任务暂停并写日志。阈值固定常量即可，暂不在 Popup 增加调频参数。
5. 验证不同标签、索引与导出之间冷却共享；认证问题、页面刷新和账号切换不能破坏隔离。无需触发真实 429。

注意：不要求把所有普通页面请求全都序列化为单并发，冻结要求是**同账号批量详情单并发**及相关批量请求遵守共享冷却；避免过度重构。

### P1：Popup 进度显示完整性

- 现有：任务类型、状态、已完成/总数、成功/失败数、已保存 ZIP 卷数；冷却截止时间在 Popup 顶部汇总。

- 保留目前“已发起下载”与“已在浏览器保存成功”的语义区别。

### P1：全文搜索引导、输入防抖及仅本地预览

1. 首次进入“全文搜索”且当前账号从未授权：明确显示首次索引说明和可点击授权入口；**不自动触发批量抓取**。可保留现有“首次索引（需授权）”按钮，无须再叠加复杂弹窗；用户点击后才确认并开始。
2. 搜索可在索引完成一部分时使用，也可在任务暂停时继续查询已有记录；保留旧版未归属索引独立开关。
3. 增加轻量输入防抖（建议 250–350ms）与小型最近查询结果缓存，切换账号、索引版本改变、手动清索引时必须失效；避免输入时重复对全量本地索引扫描。不要引入搜索服务或预先上倒排索引。
4. 对“仅本地”结果提供**本地完整内容预览**入口（从当前账号本地 JSON 读取；无缓存时明确提示）；现有片段、MD/JSON 导出和手动清理仍保留，绝不能因预览访问已确认删除的官方详情接口。
5. 在线结果继续支持消息定位；待核实、仅本地、旧索引未归属三种状态要保持区分，不能将 404 或目录缺失直接认定为官方删除。
